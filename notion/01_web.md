# **첫 번째 발자국: 웹사이트 제작, 관찰, 그리고 담금질까지**

모든 프로젝트의 시작은 사용자와 만나는 ‘얼굴’을 만드는 일이었어요. "어떻게 하면 사용자가 우리 서비스를 편하게 이용하고, 그 경험을 우리가 더 좋은 방향으로 발전시킬 수 있을까?" 하는 고민에서 웹 개발 여정이 시작됐습니다. 이 글은 그 고민의 결과물인 웹사이트 구성과 사용자 로그 수집, 그리고 시스템을 단단하게 만든 경험을 담은 일기 같은 기록입니다.

## **제가 그렸던 큰 그림**

처음 구상했던 건 간단했어요. 사용자가 웹사이트에서 무언가를 클릭하거나, 검색하거나, 로그인하는 모든 행동이 우리에겐 소중한 데이터라고 생각했죠. 그래서 이런 흐름을 만들었습니다.

1.  **사용자의 방문**: 사용자가 제 웹사이트(React로 만들었어요)에 들어옵니다.
2.  **API 요청**: 로그인이나 추천 같은 기능이 필요할 때, 웹사이트는 똑똑한 비서인 FastAPI 서버에게 일을 시킵니다.
3.  **흔적 기록**: FastAPI는 요청받은 일을 처리함과 동시에, "어떤 사용자가, 언제, 무엇을 했다"는 기록을 JSONL이라는 깔끔한 메모장에 한 줄씩 적어둡니다.
4.  **안전한 보관**: 이 소중한 기록들은 나중에 더 큰 분석을 위해 MinIO S3라는 안전한 창고에 차곡차곡 쌓이도록 설정할 수도 있게 만들었어요.

마치 제가 걸어가는 길에 작은 조약돌을 하나씩 놓아두는 것처럼, 사용자의 모든 여정에 흔적을 남기는 거죠.

## **어떤 흔적들을 남기기로 했을까?**

사용자의 모든 행동을 기록할 순 없으니, 의미 있는 행동들을 추려내는 과정이 필요했어요.

-   **가장 기본적인 흔적**: 어떤 페이지를 봤는지(`page_view`), 어디를 클릭했는지(`ui_click`) 같은 기본 행동부터 기록하기로 했어요. 이건 마치 "어디를 둘러보고, 무엇에 관심을 보였나"를 아는 것과 같아요.
-   **조금 더 특별한 흔적**:
    -   로그인을 시도하고 성공했는지(`login`), 실패했는지(`login_fail`).
    -   추천 시스템이 잘 작동했는지(`category_recommendation`), 혹시 오류는 없었는지(`recommendation_error`).
    -   사용자가 어떤 콘텐츠를 보기 시작하고(`watch_progress`), 끝까지 다 봤는지(`video_complete`).
    -   검색창에 무엇을 입력하고(`search_query`), 어떤 결과에 흥미를 느꼈는지(`search_keyword_click`).

이런 구체적인 흔적들이 모여야 사용자의 의도를 더 깊게 파악할 수 있을 거라고 믿었어요.

## **뒷단에서는 어떻게 이 흔적들을 다뤘을까?**

FastAPI 서버는 묵묵히 제 역할을 해줬습니다. 프런트엔드에서 "이런 일이 있었어!" 하고 알려주면, 서버는 그 정보를 받아서 **언제, 어떤 IP 주소에서, 어떤 브라우저로 접속했는지** 같은 추가 정보를 덧붙여 파일에 기록했어요.

혹시나 추천을 해주다가 에러가 나거나, 로그인에 실패하는 안타까운 상황이 생겨도 놓치지 않고 `recommendation_error`나 `login_fail` 같은 흔적을 남겨서 나중에 "왜 그랬을까?" 하고 원인을 찾아볼 수 있도록 준비해뒀죠.

## **이 과정을 통해 제가 배우고 사용한 것들**

이번 웹 개발 여정을 통해 몇 가지 중요한 개념들과 다시 한번 친해질 수 있었어요.

-   **API의 소중함**: 정해진 주소(`api/…`)로 요청을 보내면 정해진 일을 처리해주는 API 덕분에 웹사이트와 서버가 질서정연하게 대화할 수 있었어요.
-   **JSON Lines (JSONL)**: 수많은 기록을 한 파일에 계속 추가해야 할 때, 한 줄에 하나씩 JSON을 적는 이 방식이 정말 효율적이었어요. 나중에 데이터를 처리할 때도 편했고요.
-   **로그는 조용히**: 만약 로그를 남기다가 문제가 생겨더라도, 사용자에게는 아무런 영향이 없어야 한다고 생각했어요. 그래서 로깅 작업은 실패하더라도 조용히 넘어가도록(`try/ignore`) 처리했습니다.

## **데이터 파이프라인의 심장 박동을 확인하는 계기판: 어드민 페이지**

데이터를 쌓기 시작하니 새로운 궁금증이 생겼습니다. "그래서, 데이터는 지금 잘 쌓이고 있는 걸까? 혹시 어디선가 막힌 건 아닐까?" 매번 서버에 접속해서 파일을 열어볼 수는 없는 노릇이었죠. 그래서 데이터 흐름의 건강 상태를 한눈에 볼 수 있는 어드민 페이지를 만들기로 결심했습니다.

이 페이지를 만든 이유는 두 가지였습니다.
1.  **헬스 체크**: 데이터가 잘 수집되고, 잘 정제되는지 실시간으로 확인하고 싶었어요.
2.  **빠른 데이터 확인**: 문제가 생겼을 때, 원본 데이터는 어떻게 생겼는지, 정제된 데이터는 어떤 모습인지 바로 보고 싶었죠.

그래서 이런 기능들을 추가했습니다.

-   **핵심 지표 카드**: 원본 로그는 몇 줄인지, 정제된 데이터는 몇 개인지, 총 몇 명의 사용자가 있는지 등을 숫자로 바로 보여줘서 시스템이 건강한지 10초 만에 파악할 수 있게 했습니다.
-   **원본 로그 뷰어**: "혹시 로그가 깨져서 들어오나?" 싶을 때, 최근 수집된 원본 JSONL 로그 몇 줄을 바로 화면에서 볼 수 있게 만들었어요. 포맷이나 값 검증에 정말 유용했죠.
-   **간이 SQL 실행기**: 정제된 데이터는 Postgres 데이터베이스에 쌓이는데, 복잡한 BI 도구를 켜지 않고도 간단한 `SELECT` 쿼리로 데이터를 확인하고 싶었습니다. 그래서 어드민 페이지에 작은 SQL 편집기를 넣었죠.

    ```sql
    -- 예시: 최근 발생한 이벤트 5개를 확인하고 싶을 때
    SELECT * 
    FROM mart.events
    ORDER BY event_timestamp DESC
    LIMIT 5;
    ```
이 어드민 페이지는 제게 자동차 계기판과 같은 역할을 해주었습니다. 데이터 파이프라인이라는 복잡한 시스템이 지금 어떤 속도로, 어떤 상태로 달리고 있는지 알려주는 고마운 존재가 되었죠.

## **우리 시스템은 얼마나 튼튼할까? 트래픽 테스트 대작전**

시스템을 다 만들고 나니, 문득 이런 생각이 들었습니다. "만약 사용자가 갑자기 몰리면, 내 시스템은 버틸 수 있을까?" 특히 이벤트 로그를 수집하는 부분은 수많은 요청을 한꺼번에 받게 될 수 있으니, 미리 테스트해보고 싶었습니다.

그래서 간단한 트래픽 발생 도구를 만들었습니다. `/traffic` 이라는 숨겨진 페이지에 접속하면, 특정 URL에 원하는 만큼 요청을 보내 시스템을 테스트해볼 수 있는 장난감 같은 도구였죠.

-   **어떻게 동작하나?**: 테스트하고 싶은 URL, 총 몇 번의 요청을 보낼지, 한 번에 몇 개의 요청을 동시에 보낼지 등을 입력하고 버튼을 누르면, 이 페이지가 열심히 백엔드에 요청을 보냅니다.
-   **안전장치는 필수**: 혹시나 실수로 너무 과도한 부하를 주어 시스템 전체가 멈추는 것을 막고 싶었어요. 그래서 코드에 최대 요청 수와 동시 실행 수를 제한하는 안전장치를 걸어두었습니다.

    ```javascript
    // traffic.html의 스크립트 일부
    function startTraffic() {
      const totalRequests = parseInt(document.getElementById('total').value, 10);
      const concurrency = parseInt(document.getElementById('concurrency').value, 10);
      
      // 최대 2만 건, 동시 200건으로 제한
      if (totalRequests > 20000 || concurrency > 200) {
        alert("과도한 요청입니다. 총 요청은 20,000건, 동시 실행은 200건 이하로 설정해주세요.");
        return;
      }
      // ... (요청 시작 로직) ...
    }
    ```
이 테스트 덕분에, 저는 제 데이터 파이프라인이 어느 정도의 부하까지 감당할 수 있는지 미리 파악하고, 병목 지점을 찾아 개선할 기회를 얻을 수 있었습니다.

## **혹시 저와 같은 길을 걷는 분들에게**

만약 비슷한 시스템을 만든다면, 이것부터 시작해보세요.

1.  코드를 짜기 전에, **"어떤 사용자 행동이 궁금한가?"**를 먼저 종이에 적어보세요.
2.  그다음, 각 행동에 `page_view`처럼 쉬운 이름을 붙여주고, 어떤 추가 정보가 필요한지 정리해보세요.
3.  이 약속을 바탕으로 프런트엔드에서는 `trackEvent("이름", {정보})` 함수를, 백엔드에서는 받은 정보를 파일에 쓰는 로직을 구현하면 된답니다.
4.  데이터가 쌓이기 시작하면, **반드시 그 흐름을 감시할 수 있는 어드민 페이지**를 만드세요. 문제가 터지기 전에 발견할 수 있습니다.
5.  마지막으로, **자신이 만든 시스템을 스스로 공격해보세요.** 부하 테스트는 시스템의 약한 고리를 찾아내는 가장 좋은 방법입니다.

이렇게 첫 단추를 꿰고, 관찰하고, 끊임없이 담금질하는 과정을 통해 시스템은 비로소 살아 움직이며 단단해지기 시작했습니다.
